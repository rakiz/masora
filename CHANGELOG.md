## [Unreleased]

### Added

- `masora facts --repo [--symbol]` implemented (`masora/facts.py`) — the Masora side of the cppgraph injection contract (docs/CPPGRAPH_INTEGRATION.md §3) is no longer delivery pending: strictly read-only (never builds the index, never touches the network), it resolves the base from the user config for `--repo` (mappings on the normalized `origin` remote, then `default_base` — `write.auto_base()` factored out of `resolve_base` and shared with the MCP write tools; no base parameter per contract §4), reads the existing per-checkout index and prints ONE compact JSON document `{contract_version: 1, repo_head, graph_commit, stale_warning, facts[]}` on stdout. `--symbol` (exact SCIP identity, matched verbatim) filters to lineages whose effective version anchors on it — the displayed version, or the NEWEST version for `resolution: none` / founderless-unknown lineages where `displayed` is null — and fills `anchors_matched`; without it every lineage is returned with `anchors_matched: []`. The two warning classes are in-band and never errors: `stale_warning` = the `index_stale()` three-axis drift comparison (base HEAD / repo HEAD / graph indexed commit vs recorded; `null` when nothing is comparable) and provider unavailability surfaces as per-lineage `unknown` flags. Hard failures exit 1 with the diagnostic on stderr and NOTHING on stdout (contract §5): `E-FACTS-NO-BASE` (new: no base resolved, broken mapping/default_base, unreadable config), `E-FACTS-NOINDEX` (new: no index for the base × repo pair — build with `masora index`), reusing `E-IDX-CORRUPT` and `E-IDX-REPO`; both new codes documented in docs/TROUBLESHOOTING.md in the same change (two-way guarded). Contract doc amended: status shipped, §5 wording (never builds), §3 resolution row already includes `unknown`; ARCHITECTURE.md gained the facts-command section. 11 facts tests (CLI-level, hermetic `MASORA_HOME`, real git repos + a `write_graph_db` fixture graph), 394 total green.

- docs: cppgraph injection handoff contract — docs/CPPGRAPH_INTEGRATION.md pins the `masora facts --repo [--symbol]` surface for the agent implementing injection inside the cppgraph repo (versioned JSON, `contract_version: 1`: `{contract_version, repo_head, graph_commit, stale_warning, facts[]}` with per-fact status tuples, discovery via the user config only — cppgraph passes `--repo` and never locates bases —, the two warning classes in-band and never errors (`stale_warning` / per-lineage `unknown`), rendering rules with the negative-knowledge `NOT:` envelope and a ≤ 2-facts / ≤ 60-token budget, read-only/no-SQL-parsing invariants, and a shipping checklist); the command is delivery pending and tracked in TODO.md.

- MCP server + write path implemented: `masora mcp` runs a hand-rolled minimal MCP stdio server (`masora/mcp.py`) — newline-delimited JSON-RPC 2.0, no SDK and no new runtime dependency (MASORA_DESIGN.md §12.9), protocol version pinned to `2025-06-18` and negotiated the standard MCP way (the initialize result always carries it; malformed initialize params are -32602), methods `initialize` / `notifications/initialized` / `tools/list` / `tools/call` only, JSON-RPC errors mapped (-32700 parse with resilience — a malformed line never stops the loop, reported as `W-MCP-PROTO` on stderr —, -32600 invalid request, -32601 method not found, -32602 invalid params/unknown tool, -32603 internal); tool failures are MCP results with `isError: true` carrying diagnostic codes, never protocol crashes. The five write tools (`note`, `verify`, `doubt`, `undoubt`, `refute`) share ONE event-writing path (`masora/write.py`): base resolution honours an explicit `base` parameter first, then matches the code repo's normalized `origin` remote against the config `[[mappings]]`, then `default_base`, else `E-MCP-NO-BASE` asks for one (§9 — no guessing); `note` resolves anchor refs through the graph provider (exact SCIP match, else case-insensitive substring; `ambiguous`/`not_found` → `E-MCP-ANCHOR` with candidates, nothing written, FORMAT §6), records write-time fingerprints + edge/neighbour snapshots via `masora/providers.py` (completing the provider-task caveat; §11 `resolve(ref)` added), and refuses a graph behind HEAD or absent with `E-MCP-GRAPH` (§5.2, message: re-index cppgraph) — without anchors only an explicit `unanchored: true` + reason writes; events are pre-validated (`schema.validate_event`) behind a shared `check_base` pre-check (nothing is written onto an invalid base), emitted in canonical block-style YAML with JSON-style control-char escaping (multi-line statements round-trip), written to `<YYYY-MM>/<lineage>/<id>.<kind>.md`, and followed by a full post-write `check_base` whose failure unlinks the just-written file — a tool never returns success on an invalid tree; timestamps always carry `graph_commit` (explicit null when no graph was available, FORMAT §4); `verify` targets a claim version, `doubt` a verify, `refute` any event — a lineage id (including the founding claim's, whose id equals the lineage) rides the fold to the lineage's DISPLAYED version (or its active verify for doubt) and re-fingerprints the immutable anchor set, refusing drift with `E-MCP-DRIFT` (write a new claim version instead, §6.3) while recording fresh per-anchor snapshots; `undoubt` targets the doubt's ULID only. `search` runs FTS over the index and `list_stale` lists lineages whose resolution is not current/none — both resolve the base the same way, auto-build a missing index, and surface `W-IDX-STALE` in the result text without rebuilding (the SessionStart hook owns freshness). New diagnostics `E-MCP-ARGS`, `E-MCP-NO-BASE`, `E-MCP-GRAPH`, `E-MCP-UNKNOWN-ID`, `E-MCP-ANCHOR`, `E-MCP-DRIFT`, `W-MCP-PROTO` documented in docs/TROUBLESHOOTING.md in the same change (two-way guarded); ARCHITECTURE.md gained the MCP section, README the register-the-server line, MASORA_DESIGN §12 the settled transport decision; 39 MCP tests (subprocess-driven server over real git repos + a `write_graph_db` fixture graph, hermetic `MASORA_HOME`, rapid-consecutive-note ULID monotonicity), 383 total green.

- `code` anchor provider over a cppgraph graph store implemented (`masora/providers.py`): the default index registry now ships `code` entries for both the fingerprint registry and the edge-snapshot registry — the newest `<repo>/.cppgraph/*.graph.db` (store schema v5: `files`/`symbols`/`edges`/`meta`, learned from the cppgraph source) is opened read-only and the FORMAT.md §4 anchor identity (the SCIP symbol string, opaque-but-structured) is matched verbatim against `symbols.symbol`. Definition fingerprint: sha256 of the whitespace/comment-normalized source of the definition range `symbols.line`..`end_line` (0-indexed; single definition line on stores without body extents — stock binaries); edge-set fingerprint: sha256 of the sorted distinct callee SCIP strings of `calls` edges only (§5.4); neighbour snapshot: 1-hop callers ∪ callees mapped to their edge-set hashes (§12.4) — `suspect` now fires for real on call-neighbourhood drift. Currency policy (§5.2): the store's `meta.source_commit` must equal the `--repo` git HEAD, decided once per index build for ALL code anchors (never per-anchor: the registry contract has no per-anchor availability channel — callable None means `not_found` — and §5.2 refuses fingerprints from a stale graph wholesale); mismatch/unverifiable → `unknown` shadows + `W-IDX-GRAPH` stating why (new code, documented in docs/TROUBLESHOOTING.md in the same change); a missing graph store stays silent `unknown` (cppgraph is optional). CLI `masora index` gains `--cppgraph <db>` (explicit store) and `--no-cppgraph` (force file-only); the used graph commit is exposed on the result and in the index meta (`graph_commit`, `graph_db`). `W-IDX-STALE` now also fires at search time when the code state moved since the build — stored `repo_head`/`graph_commit` (recorded alongside `base_head` in the index meta) compared against the current `--repo` HEAD and the discovered graph store's indexed commit; unknown sides are skipped (no `--repo`, pre-provider index rows, no discovered graph). 24 new tests (17 provider-level over hand-crafted graph stores, 7 through the full index path — including the pinned code=unknown tests now resolving with a fixture registry, and `suspect` firing on neighbour and own-edge drift between two graph builds), 337 total green.

- Settled the open questions Q1–Q5 and Q7 of MASORA_DESIGN.md §12 with the design owner: v1 covers structural and semantic claims (semantic = auto-doubt only); the LLM may verify any claim backed by recorded evidence (replayed proof query or pointers to the proving code + explanation), humans override via refutation and PR review; anchors are symbols only, multiple per claim; `suspect` fires on a 1-hop edge-set change against a persisted neighbour snapshot; the provider interface fixes outcome semantics (`resolved`/`not_found`/`unavailable`/`ambiguous`) and digest-based `url` validity. Q6 and Q8 stay postponed.
- Verification is now a `.verify` event (fourth event kind) instead of a claim frontmatter field: no `.md` file is ever modified after creation, promotion and re-verification append files, and a version's fingerprint set is immutable.
- SPEC.md updated accordingly (event kinds, verification authorship, symbol-only multi-anchor rule + neighbour snapshot, `suspect`/`unknown` statuses, provider outcome semantics, edge/subgraph anchors out of scope).
- User-journey review with the design owner: added `.doubt`/`.undoubt` events (human disagreement with a verified version = doubt, not refutation); layout relaxed to convention-only (content-based validation, moving files changes nothing); one shared base per team as the default story (multi-base kept as config capability); publication via one branch + one PR with local `masora check`, no CI in v1; `masora gc` for cleanup; install UX aligned with cppgraph (`setup.sh`); mapping-fallback rule for projects with no matching remote.
- Onboarding gap closed: a base declares itself via `base.toml` (name + served code remotes) at its repo root; `masora setup --base <url>` writes the local config from it in one command — the base URL travels through the team's onboarding docs, nothing lives in the code repo.
- Rollout decided: the first base lives on the author's `employees/` dir, install explained on a Confluence page, migration to a dedicated repo proposed if adopted.
- Provenance du modèle : champ optionnel `model` (chaîne libre, ex. `glm-5p3-flash`) sur les claims et les `.verify` quand l'auteur est un LLM — `cost_tokens` se lit contre lui (48k de GPT-6-astra ≠ 48k de DeepSeek-4.1-flash) ; le modèle de vérification peut différer du modèle d'écriture.
- Source version on claims: `recorded_at {commit, graph_commit}` added to the claim schema (the write-time commit was stated in §10.2 but absent from the field list); commits qualify, fingerprints still decide.
- Same-type schema holes found in a systematic sweep and fixed: anchors carry their write-time edge-set hash (`edges`) — required by the `suspect` rule but previously homeless; `unanchored` claims get an explicit resolution rule (no fingerprint resolution, always surfaced, flag as validity signal); §7 example and §5.1 aligned with the immutable-fingerprint `.verify` model; `cost_tokens` is agent-provided, never invented by the tool.
- FORMAT.md, the canonical event-file contract, frozen after a full audit chain (cheap-review consistency → design-review REWORK → strong-review systemic audit → cross-vendor strong-review-alternative → two verification passes, final 0 MAJOR): six block-style templates, per-kind required/optional/forbidden table, YAML canonicalization, monotonic Crockford ULIDs with clock-free cycle rejection, per-anchor provider-neutral snapshots (code: edge set + per-anchor neighbours), active-event folding as a backward descending-ULID fixed point, `deleted.toml` tombstones, standalone-check vs sync baseline rules.
- `masora check` MVP implemented against the frozen contract: standalone whole-tree validation (schema per kind, canonicalization, cross-file references, cycle rejection, founder resolution, tombstones) + §6 fold producing per-claim status envelopes; the fold rule is proven by an executable spec — brute force over all 13,512 event-graph DAGs at n≤4 against an independent topological oracle (order-independence across 4 evaluation orders) plus 10,000 sampled 5-event DAGs; 190 tests green. Review pipeline (1 MAJOR neighbour-hash quoting + 6 MINOR) applied and verified. The executable spec fed a contract correction back into FORMAT.md §6 (convergence scoped to the acyclic domain).
- `masora sync` implemented: publication batches local events onto the `masora/pending` branch (plumbing commit, force-with-lease push) and opens or updates the single PR (`gh` when available, compare-URL fallback), with solo direct-push (`--push`) and explicit discard (`--drop`). Sync runs the local whole-tree check first, then the append-only content diff by event-id identity against the merge-base (rewrites and deletions are tampering; whole-lineage deletions report `E-GC-UNAVAILABLE` until `masora gc` exists; tombstone shrink vs merge-base rejected), the founder rule for new v2+ claims, and merged-result validation on origin/main + pending overlay with a union tombstone so gc-vs-extension races are surfaced before publication. 27 sync tests, 220 total with the documentation suite; review pipeline applied (2 MAJOR: deletions diffed against origin/main instead of the merge-base, solo push leaving the local repo inconsistent — both fixed and verified).
- Final audit (strong-review, verdict NO-GO then GO-with-reservations once fixed) applied to the docs: `.refute`/`.doubt` may target any event ULID (a refuted `.verify` is ignored when folding); computed status defined as a tuple (resolution × verification × flags) replacing three divergent status lists; negative-knowledge envelope (`NOT: <summary> — refuted: <reason>`) added, resolving the injection contradiction; replay re-timed to verify/check (never reindex), all `--ci` mentions removed; proof-query format fixed (`{tool, args, expect, provider_version}`, set equality, tool whitelist); fingerprint contract specified (normalized definition text, sorted callee SCIP strings of `calls` edges, graph commit recorded, refuse writes from a stale graph); `setup --base <url>#<path>` supports sub-directory bases; pending-event lifecycle defined (`masora/pending` branch, one PR updated, squash-safe, `sync --drop`); doubt uses `source` (not actor); ULID chosen over UUIDv7; `gc` manual-only in v1; MCP/CLI tool surfaces harmonized.
- Project documentation: README.md (what/why, Masoretes story, event lifecycle, quick start), docs/ARCHITECTURE.md (per-module walkthrough with FORMAT.md section references, including what is not built yet), docs/TROUBLESHOOTING.md (one row per diagnostic code: meaning, cause, remedy), AGENTS.md (AI-session read-order and invariants), and tests/test_docs.py which pins the troubleshooting table to masora/diagnostics.py in both directions so they cannot diverge. scripts/docs_check.sh runs a docs-freshness agent check on demand (manual step before proposing a commit; kept out of the pre-commit hook to avoid concurrent git access).
- Hardened every git spawn (masora/sync.py, test helpers) against inherited repo-location GIT_* variables (GIT_DIR, GIT_WORK_TREE, GIT_INDEX_FILE, ...) via masora.sync.git_env(); a stray export could make the test suite pollute the parent repo's index. Session-start fixture in tests/conftest.py as a second net; regression test in tests/test_sync.py.
- `masora setup --base <url>[#<path>]` implemented: onboarding in one command — partial clone + sparse checkout of the base into `~/.local/share/masora/bases/<name>` (root bases widen to the full tree; a sub-directory base is the sparse-checkout root), `base.toml` read and validated (settled schema: `name` + `code_remotes`, exactly these keys), and the local `~/.config/masora/config.toml` written or merged (`[bases.<slug>]` from remote/path/clone-HEAD branch + one `[[mappings]]` block per served code remote, `code_remote` stored normalized; existing entries, mappings and unknown keys preserved; same-remote re-run updates in place, a different remote under the same name is refused). Remote normalization (lowercase host, no scheme, no user/port prefix, no trailing `.git`) lives in `masora/config.py` for reuse; `MASORA_HOME` relocates config and clones for tests and special cases. Seven new `E-SETUP-*` diagnostics (arg, clone, missing base.toml, base.toml schema, unreadable config, unwritable config, duplicate base) documented in docs/TROUBLESHOOTING.md in the same change; 17 setup tests over real git repos, 238 total green.
- `masora gc --lineage` implemented: whole-lineage deletion on explicit, confirmed request (no auto-suggestions in v1 — a fully-refuted lineage is negative knowledge). Plan-then-confirm CLI (`--lineage` repeatable; plan mode prints the event files, the tombstone blocks and a `W-GC-ACTIVE` warning for still-active lineages, exits 3 without writing; `--yes` executes); `masora check` runs before (errors block) and after (failure = `E-GC-CHECK`) the mutation; one `[[deleted]]` block per lineage `{lineage, ulids}` is appended to `deleted.toml` (append-only by content), the lineage's event files are removed and emptied parent directories pruned; gc commits nothing — the deletion is an ordinary git commit left to the user, or travels through `masora sync` like any pending change. `sync` now accepts whole-lineage deletions whose lineage is tombstoned in the local `deleted.toml` (FORMAT.md §7.10) and applies them to the merged tree before merged-result validation; deletions without a tombstone keep failing (`E-GC-UNAVAILABLE`, message updated: it is tampering, use gc). New diagnostics `E-GC-ULID`, `E-GC-UNKNOWN`, `E-GC-CHECK` and `W-GC-ACTIVE` documented in docs/TROUBLESHOOTING.md in the same change; 12 gc tests including the keystone (sync accepts a gc'd base), 254 total green.
- SQLite index + §6.2 resolution + FTS implemented: `masora/resolve.py` computes the full status tuple per lineage (resolution `current`/`stale`/`restored`/`none`, verification `verified(<actor>)`/`unverified`, flags `suspect`/`doubted`/`pending`/`unknown`/`unanchored`) as pure functions over parsed lineage data, reusing `masora/fold.py` (activity fixed point, refute/unrefute/doubt folding, founder-absent exclusion, precedence `none` > `unknown` > `current`/`restored` > `stale`); anchor providers are injectable registries (missing/None entry = unavailable → `unknown` shadows instead of guessing; callable returning None = not_found → fails to match); `suspect` (§12.4) compares the displayed version's newest snapshot (newest active verify, else write-time) against current edge-set hashes over the union of recorded and current neighbours. `masora/index.py` persists it: full-rebuild-only SQLite DB (WAL, atomic replace, safe to delete anytime) at `<masora_home>/indexes/<base-slug>/<repo-slug>-<path-hash>.db` — one index per base × code repo — with `check_base` gating, tombstoned-lineage exclusion, schema `meta`/`lineages`/`versions`/`anchors` + FTS5 `search` (summary + statement, case/accent-insensitive), and stored base HEAD powering `index_stale()`/`W-IDX-STALE`. Providers shipped without cppgraph: the `file` provider hashes whitespace/comment-normalized content of the `--repo` checkout (a reformat must not stale claims, §5.2); `code` anchors have no provider yet and report `unknown`, never a guessed status. CLI: `masora index <base-dir> [--repo <path>]` (summary counts by status) and `masora search <base-dir> <query> [--repo <path>]` (FTS rendering with status tuples — the human/test-visible surface; MCP tools come later). New diagnostics `E-IDX-REPO`, `E-IDX-WRITE`, `E-IDX-CORRUPT` (auto-rebuild on index, refuse on search), `E-IDX-NOINDEX`, `E-IDX-QUERY` (arg-level error), `W-IDX-CORRUPT`, `W-IDX-STALE` documented in docs/TROUBLESHOOTING.md in the same change; 58 new tests (32-case §6.2 matrix incl. suspect/doubted/pending/unrefute/founder-absent, FTS match/case/accent/no-match/tombstone/query-syntax-classification, rebuild idempotence, DB deletion + corruption recovery, base-HEAD staleness, pending via origin diff, comment/reformat-normalization invariance), 313 total green.
